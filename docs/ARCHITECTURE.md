# Wildcraft 架构与工作流计划

这份文档记录当前实现和后续设计边界。P1 提供历史等级与精力，P2 提供攀爬，P3 增加独立伞槽、装备保存、双手与滑翔，P3.1 增加三类背负、最小展示同步和左上角红心/精力；P0 物品回归与 R0 隔离研究保留。其余玩法包按阶段创建，避免先建立空框架。

2026-10-02 的方向调整见 [开发规划 v2](DEVELOPMENT-PLAN-V2.md)。背负装备和左上角 HUD 已在 P3.1 实施；正式林克时间与轻量环境温度仍为后续目标。本文件中的 P1–P3.1 说明描述当前行为。旧路线中的温度/料理泛化表述按新规划收敛，不据此引入普通冷热伤害。

## 新规划对架构的约束

- 林克时间增加服务端资格/费用和单人时间接管职责。先经 R1 验证世界时间、玩家输入、弓蓄力和精力计费的边界，再实现；多人不能复用全服减速。临时会话不持久化，退出只撤销自己的时间控制。
- 背负装备只维护三个指向真实库存的视觉记录，不增加容量。服务器同步必要展示数据，客户端复用物品渲染；既有滑翔伞真实装备附件保持独立。渲染判断要区分“物品仍在手槽”与“当前画面中实际手持”。
- 温度目标值与玩家负面状态分离。P4A 读取群系、当地天气、水和热源并平滑显示；P4B 的保暖料理辅助原版细雪，不建立普遍冷热伤害，也不让普通电池/机械承受冷热惩罚。
- P3.1 按用户最新决定把原版红心移到左上角，精力短条放在其下；原版经验和骑乘条保留底部区域。P4B 先接通料理效果和时长，P9.1 再补齐已选的临时精力上限/降耗等联动；实现临时上限时不能只改显示而继续按基础上限截断，不能删除已有格式 1 读取。
- `equipment` 已建立；`focus` 和其他渲染职责按阶段建立；不在规划阶段生成空包或建立万能技能框架。具体数据、时间和同步合同以新规划第 5–9 节为准。

## 版本与工具策略

当前基线固定为 Minecraft 26.3、JDK 25、Fabric Loader 0.19.5、Fabric API 0.161.0+26.3、Loom 1.18.2 和 Gradle Wrapper 9.7.1。Wrapper 校验下载校验和，开发与持续构建使用同一工具版本。Loom 使用稳定发布，不跟随模板的快照版本。

Minecraft 与 Fabric 作为一组升级。在升级分支中先运行 P0，再验证玩家数据、移动、存档和网络协议；第三方能力尚不支持时继续使用已验证的基线。预览版只用于隔离研究。当前官方开发文档可能落后于游戏版本，具体类名与入口以本项目锁定的 API 和游戏代码为准。

macOS 使用 IntelliJ IDEA 的 Gradle 导入和 JDK 25。终端通过 `dev.sh` 选择 JDK，不修改其他项目的 Java 配置。Gradle 管理下载和构建，不需要全局安装另一个 Gradle。资源制作优先使用 Blockbench 的 Java 模型与原始工程文件；简单图标采用原版物品模型。

## 目录和模块

维持单一 Gradle 项目和一份 Mod JAR，使用 Fabric 的公共与客户端来源分离。公共代码禁止引用 `net.minecraft.client`。

```text
src/main/java/dev/wildcraft/
  Wildcraft.java       公共入口
  registry/            注册对象
  player/              玩家进度、精力和专用滑翔装备位
  mixin/               经验、移动与装备菜单的必要原版拦截
  traversal/           攀爬与滑翔的服务端状态
  equipment/           背负三类登记、真实引用、保存与展示同步
  cooking/             料理配方与效果
  temperature/         环境温度与玩家响应
  fuse/                融合数据与宿主适配
  energy/              能源、充放电与计量
  machine/             主体、部件、节点、安装和拆卸
  fabricator/          古代装置制造机
  weather/             风场与天气的规则
  network/             输入请求与状态同步
src/client/java/dev/wildcraft/client/
  input/               按键与操作请求
  hud/                 精力与电量显示
  render/              物品、玩家和机械外观
  screen/              料理、设备与制造机界面
  datagen/             模型、语言、配方与标签生成
src/main/resources/    元数据、手写贴图和声音
src/main/generated/    可重建的生成资源
src/gametest/          游戏行为和客户端验证
src/rulesTest/         不启动游戏的纯精力数值验证
art/source/            模型、贴图、动画原始文件
docs/                  决策、路线与验证记录
```

规则计算尽量不依赖渲染和世界对象。机械与探索系统通过精力、电量和天气的明确输入协作，不建立万能事件总线或插件框架。

当前正式代码包含入口、注册、`player`、`traversal`、`equipment`、`network`、`mixin` 与客户端 `input`、`hud`、`render`、`datagen` 和客户端 Mixin；目录图中的其他玩法包表示后续职责。R0 注册项和研究实体仅在 `src/gametest` 中存在，不进入玩家安装的 JAR。

## 客户端与服务端边界

| 系统 | 服务端负责 | 客户端负责 |
| --- | --- | --- |
| 历史等级、精力 | 峰值、容量、消耗、恢复、死亡处理 | HUD 和反馈；P1 不预测数值 |
| 攀爬、滑翔 | 接触、装备、状态转换、移动约束、耗尽 | 输入、镜头、动画与预测 |
| 背负装备 | 实际使用登记、真实所有权、引用失效与最小同步 | 原版物品挂载；不以外观相同推断身份 |
| 料理、温度 | 验证材料、扣除、产出、效果、环境采样 | 界面、预览、状态提示 |
| Fuse | 验证宿主与材料、消费、保存、属性与攻击效果 | 组合预览、名称、动态外观 |
| 能源和电池 | 充放电、速率、剩余电量、供能条件 | 电量显示与运行外观 |
| 机械 | 节点有效性、安装距离、部件清单、运行与回收 | 目标提示、操作请求、插值和渲染 |
| 制造机 | 一次性投入、固定结果、库存输出与中断恢复 | 操作界面和进度 |
| 风与天气 | 风场参数、效果与更新频率 | 同步后的表现、插值与音效 |

客户端发送操作意图，不上报“最终电量”“最终伤害”或直接指定奖励。服务端校验玩家、距离、物品、状态、库存和速率。输入包有固定字段和上限；重复请求不能再次消费、产出或回收。界面、按键和渲染类只放在客户端来源中。

高频移动先使用原版移动路径和必要的 Fabric 事件；确实需要拦截时再引入最小 Mixin。避免同时强行写入位置与速度导致联机回弹。运行状态变化及时同步，稳定数值按需要合并发送；不每帧广播完整机械清单。

P1 的 `PlayerStamina` 在服务端管理状态，`StaminaRules` 只计算数值，`StaminaData` 负责不可变状态与 Codec。原版设置等级、增加等级和获取经验的方法尾部记录峰值，服务端每刻再补充观察；在同一刻反复直接写字段的第三方代码仍存在无法还原历史的限制。

持久附件 `player_stamina` 不同步，包含格式版本、历史等级、当前精力与恢复等待。临时附件 `stamina_view` 只给对应玩家同步峰值和当前精力，上限由规则推导。变化中的恢复数值最多每 4 刻同步一次，容量变化、消耗和复活即时更新；相同视图不重复写入。

P2 的 `ClimbInput` 只传按住状态和两个受限方向轴；服务端 `Climbing` 根据碰撞接触、资格、精力、输入时效和抓握锁决定状态，每刻只扣一次费用。服务端观察实际位移，防止用停留输入降低移动费用。客户端按同样的几何规则预测，通过原版 `move` 与位置包移动；攀爬没有自定义位置传送协议，也没有关闭原版移动检查。`ClimbSurface` 处理实际碰撞形状、转角和墙顶空间；额外位移检查只作用于已授权的攀爬。

攀爬输入、会话和本人显示附件都不持久化，不复制成可恢复的抓握。按键变化立即发送，持续按住每 5 刻续报，20 刻超时放手；死亡、重连和切维度清理状态。P3.1 精力 HUD 挂在原版健康层之后，读取本帧多行红心底边；不依赖经验数字是否显示，0 级玩家也能看到精力。客户端包装原版红心提取方法只改变坐标，保留伤害闪烁、中毒、凋零、吸收与极限图案。

P3 沿用原版 `InventoryMenu` 点击协议，在菜单中追加 `GliderSlot`，带普通与 Shift 装卸，不占护甲或副手。`GliderEquipment` 保存独立格式 1 的完整 ItemStack，只同步给本人。装备槽在原版创造装备页定位，并单独验证新增槽的创造编辑权限、类型与数量；生存玩家不能通过创造编辑包安装装备。

`GlideInput` 只请求开合；`Gliding` 在服务端验证装备、资格、消耗、中断和手中物品变化，并对已授权移动增加边界检查。其开合附件同步给跟踪玩家的客户端，精力仍仅给本人。客户端按原版碰撞预测缓降，使用原版移动包；不设置鞘翅飞行标记，也不授予创造飞行权限。

攀爬和滑翔互斥，滑翔打开会清理抓墙。客户端跟踪跳跃键的新按下动作；物品操作先结束滑翔，服务端也监听实际使用与攻击。物品只在提取渲染状态时收起，保留原来的背包和物品组件。专用伞层与双手姿态读取提取后的状态，不从绘制阶段查询世界；客户端 Mixin 单独列在配置的 `client` 部分。

P3.1 `BackEquipment` 保存三项已知位置与完整组件签名（独立格式 1），仅在服务端使用；瞬时会话跟踪真实 ItemStack 对象，移动时才搜索库存。原版菜单复制堆栈时，仅在事务前后均能唯一定位的情况下更新引用；歧义清空，不按相同 ID 绑定备用物品。重载只验证保存位置，不恢复物品、不增加容量。

`back_equipment_view` 为跟踪范围内的观察者和本人提供白名单显示副本：模型、耐久、染色、盾图案和附魔光效；不含名称、Lore、任意私有数据、容器或装填投射物。客户端渲染使用服务端确定的手/背互斥结果，不以外观相同再次猜测物品身份。层跟随身体骨骼；可见披风隐藏背负，鞘翅隐藏中央盾/弓。拉弓时盾暂时视觉收纳，底层库存不变。

## 数据保存与回退

不引入外部数据库。使用游戏已有的持久化对象、Fabric API 和 Codec；把存档格式版本与 Mod 版本分开。

| 数据 | 保存载体 | 关键规则 |
| --- | --- | --- |
| 历史最高等级、当前精力、必要计时 | 玩家持久化 Data Attachment | 峰值只增不减；死亡复活补满；存活替换、重连和切维度保留剩余值 |
| 专用槽中的滑翔伞 | 独立玩家持久化 Data Attachment，完整 ItemStack | 不占护甲或副手；普通死亡掉落一次，保留物品时保留；开伞状态不保存 |
| 三类背负引用 | 独立玩家持久化 Data Attachment，位置与组件签名 | 不是装备库存；掉落/箱子/损坏清除，保留物品死亡和重载重新验证 |
| 电池电量、Fuse 内容、料理效果 | ItemStack Data Components | 跟随物品移动；明确堆叠、复制、拆分和容器保存规则 |
| 固定能源、充电器、制造机 | Block Entity | 随区块保存，卸载时不继续免费输出 |
| 移动机械和已安装部件 | 单一主体 Entity 的保存数据 | 保存主体、节点和库存关系；不把同一部件同时保存成可掉落实体 |
| 必要的世界级风场参数 | 世界 Saved Data 或适当的附件 | 保存种子或参数，以服务端为准；不保存整张逐格风场 |

持久数据有 `schemaVersion`；新增字段提供合理默认值，保留旧版本读取。峰值在首次加入时至少读取当前等级，后续原版升级、命令变更和其他来源的等级变化都应被观察到。消费经验不能降低已记录峰值。重连、切维度和重启不能自动补满精力或电池。

玩家复制阶段保留原数据；死亡补满、装备复制和探索状态清理在 `AFTER_RESPAWN` 的明确后置事件阶段执行。该阶段排在默认阶段的 Fabric 自动附件转移之后，不依赖入口注册先后，避免旧数据覆盖复活结果。离线不推进恢复，地面恢复和参数见 [P1 规则](P1-RULES.md)，攀爬边界见 [P2 规则](P2-RULES.md)，装备保存和回退见 [P3 规则](P3-RULES.md)。

Forge/Fabric 风格的“存任意 NBT”不是 Fuse 的最终方案。融合材料优先保存有大小限制的原始 ItemStack 信息和单独计算出的有效属性；数据组件可能包含容器、复杂信息或其他 Mod 的类型，必须研究编码、上限与缺失依赖的降级行为。未知材料默认采用明确的基础效果，不把任意属性直接转为伤害。

机械安装和拆卸按服务端的一次操作处理：先验证目标与容量，再消费或放回部件。满背包、卸载、死亡、同时操作和异常中断都不能复制部件。制造机在消费时确定并保存结果；打开界面、重连或服务器重启不得重新抽取。

升级测试先备份世界，在副本上运行；真实数据迁移按批准范围执行。旧 JAR 未必理解新数据，回退使用升级前的世界备份与对应版本组合。P0 没有自定义玩家数据，P1 首次加载初始化格式 1；本轮只操作独立测试世界，没有迁移个人存档。

## 依赖原则

正式运行目前只依赖 Fabric Loader 与 Fabric API。客户端测试使用 Fabric 官方测试模块，并和成品分开。JDK、Gradle、Loom、IntelliJ IDEA 是开发工具，不是要玩家额外安装的 Mod。

先用原版模型、渲染与动画；验证确有需要后才考虑动画库、附属界面库或配置库。先完成受限的机械主体与部件模型，再决定是否需要物理库。R0 不承诺任意连接、动态关节或复杂车辆。

添加生产依赖前，检查现有能力、锁定版本支持、维护状态、许可证、服务端支持和升级成本，向用户提交明确选择。避免仅为少量工具代码引入大型库。采用依赖后记录版本和来源，不使用动态版本号。

## 资源和模型工作流

1. 确定物品或主体尺寸、节点、操作范围，用占位图和模型验证。
2. 制作原创原始资源；Blockbench 工程、贴图源文件和导出设置一起保存。
3. 原版物品模型优先；复杂机械只在需要时增加专用渲染器。
4. 模型、物品显示定义、语言、配方和标签由数据生成维护；手写美术放在 `resources`，生成资源放在 `generated`。
5. 在游戏里检查背包、手持、掉落、不同光照、安装方向、节点遮挡和多人外观。
6. 检查资源命名、大小写、纹理路径和版权来源；过滤 macOS 附属文件。

Fuse 的能力按属性、保存和显示分别验收。任意材料可保存不代表任意模型可直接拼到任何宿主上；显示失败时使用明确的回退外观。游戏升级会影响显示定义格式，需要在升级分支重跑资源生成与实际客户端检查。

## 测试、调试和 Git

P3.1 真实双客户端实验先执行 `prepareP31Lab` 冻结游戏与测试 JAR，再分别启动 `runP31Server`、`runP31Actor` 和 `runP31Observer`。三个进程用不同 `WILDCRAFT_PROJECT_CACHE`，避免 Gradle 项目缓存互锁；运行过程中不得重新冻结或改写正在读取的 JAR。实验目录在本机 APFS 缓存，独立服务端只绑定回环地址；没有 Fabric 客户端测试调度器的两个普通游戏进程实际互相观察。生产包不包含实验入口。具体命令见 P3.1 验证。

R1 已在隔离测试模块验证单人世界减速、弓计时、独立费用、输入处理和撤销。实验的共享会话与测试开关不进入正式架构；P3.2 提取时使用服务端会话与明确同步，继续只允许未公开的单人集成服务端。结果、实测范围和后续回归见 [R1 结论](R1-FINDINGS.md)。P3.1 已按实际使用登记合同完成成品和双客户端验证，见 [规格](P3.1-SPEC.md) 与 [验证](P3.1-VERIFICATION.md)。

规则和编码使用相关单元测试；真实物品、库存、世界、安装和区块行为使用 GameTest；客户端输入、HUD、渲染和网络使用实际客户端。移动手感仍需人工游玩，自动截图不替代手感验收。

调试使用 IntelliJ 的客户端运行配置和服务端日志。使用独立测试世界；记录重现步骤、游戏版本、Mod 版本和异常首段。优先定位服务端规则、同步或渲染中的具体层次，不增加特殊判断掩盖原因。

`main` 保持可构建。功能分支用 `feature/<功能>`，修复用 `fix/<问题>`，研究用 `spike/<实验>`，游戏升级用 `upgrade/mc-<版本>`。分支短期存在，不维护单独的长期 `develop` 分支。每次提交围绕一个可审阅的变化。

版本从 `0.1.0-dev.1` 起，达到可玩里程碑后使用相应 alpha；稳定候选再进入 beta/rc。标签固定代码，构建产物标明 Minecraft 版本。发布前审查许可证、第三方资源和支持版本；本机验证成功不自动授权发布或上传。

当前 GitHub Actions 配置执行 Wrapper 校验、资源生成一致性检查和构建；构建包含纯数值检查与无图形 GameTest。桌面客户端与成品独立服务端另在本机验证。本地已运行的检查与尚未远程执行的流程分别记录；不声称配置文件存在就代表远程 CI 通过。
