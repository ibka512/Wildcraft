# Wildcraft 开发规划 v2

日期：2026-10-02。规划修订号：v2。实现基线：Minecraft 26.3 / Wildcraft `0.1.0-dev.4`，P3 提交 `2b58bfd`。

本规划把「林克时间」「背负装备显示」「温度与环境适应」三个设计纳入现有工程。P0–P3 的已有成果继续使用；新增机制尚未实现。本次只调整规划和文档，不代表游戏版本升级，也不把计划中的验收列为已通过。

## 1. 规划依据与当前状态

本次完整阅读用户提供的四份文件，原文保存在 `docs/design-inputs/2026-10-02/`，文件内容未改写：

- [初版规划](design-inputs/2026-10-02/初版规划.md)：原有技术栈、系统范围与 P0–P11。
- [林克时间 v0.1](<design-inputs/2026-10-02/Wildcraft「林克时间」机制设计文档 v0.1.md>)：空中拉弓、共享精力、单人慢动作和多人边界。
- [背负装备显示 v0.1](<design-inputs/2026-10-02/Wildcraft 背负装备显示系统设计文档 v0.1.md>)：三个视觉槽、最近使用、角色挂载与多人可见。
- [温度与环境适应 v0.1](<design-inputs/2026-10-02/Wildcraft 温度与环境适应系统设计文档 v0.1.md>)：环境反馈优先，料理辅助原版细雪。

处理顺序：用户当前明确要求与已确定操作 → 三份新机制设计 → 已实现代码及验收事实 → 初版中的建议。文档里的“建议”“例如”和后续版本设想仍保留其建议性质；不把示例箭种、参数或可选特效自动转成首版硬性要求。

| 已有阶段 | 已有成果 | 本次处理 |

| P1 | 历史最高经验等级、精力保存与恢复、HUD | 保留进度；计划扩展动作费用和料理效果，调整 HUD 呈现 |

初版中“尚无项目/JDK”“待首次验证的版本组合”属于历史状态，不再作为待办。当前本机使用 Homebrew JDK 25 与 IntelliJ IDEA；无需重建项目或重新安装开发工具。

## 2. 调整后的产品方向

Wildcraft 继续是以原版世界为基础的探索、战斗与机械 Mod。新的主循环为：

```text
经验成长 → 精力上限 → 攀爬/滑翔获得高度 → 空中拉弓与林克时间 → 落地继续探索
                         ↑                         ↑
                    料理提供辅助              Fuse 提供箭矢/武器效果

环境温度 → 提示区域差异与局部危险 → 料理提高探索容错
真实携带的装备 → 背部/腰侧显示 → 完整角色外观
红石能源 → 有限电池 → 机械组装与回收 → 扩展探索方式
```

三个新设计的作用不同：林克时间增加空中战斗；背负装备补足角色表现；温度文档重新限定原有 P4 的玩法，避免扩展为硬核体温管理。

原来明确排除的内容继续排除：究极手、时间倒流、大型 Boss、完整神庙、大型新维度、复杂剧情、大量新矿石/资源体系、小型世界事件、环境谜题、机械蓝图。超复杂机械物理继续暂缓。林克时间是减速专注，不是时间倒流。

本轮也不新增饮水、武器重量、额外背包容量、自动切武器、普遍冷热伤害、机械过热或电池低温衰减。文档中的传送箭、特殊机械高温环境等仍是后续候选，不由举例扩张首版范围。

## 5. 林克时间：首版合同

### 5.1 触发与退出

- 自动触发：玩家在空中、实际正在拉弓、精力大于零、处于可正常控制的允许状态。不增加技能按键或独立资源条。
- 地面、仅手持弓、零精力、近战动作不触发。创造飞行、鞘翅、水/熔岩、乘坐、睡眠、旁观等与既有移动模式冲突的状态先列为禁止状态，逐项验证。
- 松弓/停止使用、落地、换离弓、耗尽、死亡、切维度、退出世界或模式失去许可时结束。拉弓、瞄准、松开射箭沿用原版操作；不增加自动瞄准、追踪、伤害或暴击加成。
- 玩家继续缓慢下降，保持碰撞与累计落差约束；不得照搬滑翔的摔落距离清零，也不能通过反复拉放弓无限刷新滞空或摔落保护。
- 普通移动、跳跃、疾跑、游泳不新增精力费用；攀爬、滑翔、专注共享现有精力。内部的输入去重/状态锁只用于正确性，不变成额外技能冷却。

原文的“弓类”与背负系统的“弓/弩分类”不能自动等同。建议林克时间首版支持原版弓的持续拉弓；弩的装填、预装填和发射不同，列为独立适配，未适配时照常使用弩且不进入专注。这个建议在 P3.2 的具体玩法规格中明确后实施。

### 5.2 单人与多人

首版真减速只允许在未开放 LAN、没有其他真实玩家的集成单人服务端。连接专用服或他人的 LAN 时不进入首版专注、不扣专注费用；弓继续正常使用。单人世界准备开放 LAN 时，先退出专注并恢复自己的时间控制，不能等第二名玩家登录后才补救。

多人目标是局部林克时间，不通过降低全服 Tick 速率实现。R2 必须定义实体类型、范围、敌对/中立/宠物、攻击来源和投射物所有权，并验证两个玩家同时发动时不会叠乘减速或重复恢复。默认其他玩家及其正常输入不受真实减速；玩家发射的箭、宠物和 PvP 相关投射物不能只凭“不是玩家实体”就纳入减速。未有明确规则的对象先排除。

原文把多人局部时间列为后期，故不将其伪装为 v0.1 已具备的能力；此处是计划中的支持边界，待用户批准对应实现阶段后开发。

### 5.3 时间控制与资源计费

已检查锁定的 26.3 `ServerTickRateManager` / `TickRateManager`。2026-10-02 已完成 R1 游戏内隔离实验：真实世界减速成立，弓和费用必须使用独立计时，输入需要在单人服务端等待阶段继续处理；所有权撤销、生命周期和呈现入口已有证据。具体成功范围及正式阶段仍需回归的项目见 [R1 结论](R1-FINDINGS.md)。这不等于 P3.2 正式技能已经完成。

当前精力按服务端刻更新。简单降低世界速率，会改变每现实秒扣费、恢复和同步频率，不能直接沿用所有逐刻常量。

规划采用以下时间语义，具体实现由 R1 验证：

| 对象 | 计时原则 |
| --- | --- |
| 世界、生物、投射物、普通机械生产 | 跟随服务端的游戏时间；不能只加快产出而不加快耗电 |
| 玩家镜头和输入反馈 | 保持正常帧响应，不降鼠标灵敏度；不能只靠提高鼠标速度掩盖迟滞 |
| 林克时间费用 | 按未受人为减速放大的有效游玩时长收费；暂停、离线不扣，不信任客户端报送的时长 |
| 弓蓄力/放箭 | 保留原版曲线、弹药、耐久和附魔语义；测量减速前后的实际用时，只补偿必要计时，不重复执行整段物品使用或玩家更新 |
| 料理、恢复等待和精力增益 | 定义统一的有效游玩时长策略，在 P4B 与慢动作交叉验收；保留旧存档读取，不借此重写所有原版计时 |
| 视觉过渡、温度显示平滑 | 客户端帧级平滑，不能改变服务端最终结果 |

需要测量而非提前承诺：正常/低帧率、暂停、服务端卡顿、瞬时掉帧下的扣费与射箭。卡顿计时要有上界，不能恢复后突然扣完整段离线时间，也不能反复暂停或改速刷精力。

时间状态只在当前会话中持有。进入时记录基线和自己持有的控制状态；退出只撤销自己的改动，不把管理员或其他模组的新速率一律写成 20。已有冻结、加速测试或其他时间控制冲突时先拒绝接管。保存、异常退出及重新加载不得恢复遗留的慢动作。

减速比例、下降速度、每秒费用、最低可用高度均未在原文定数。先用可替换的研发参数测量持续时间和落地风险；不把试验参数写成已确认平衡，也不随意增设最低高度门槛限制玩家自建跳台。

### 5.4 画面、声音与无障碍

首版完整包含轻冷色、轻微降饱和、轻暗角、淡青绿色边缘、准星轻微强化、简单进入/退出声音。原文 10%–20% 降饱和属于试调范围。第一/第三人称都支持，不强制切镜头、不锁视角；FOV 变化轻微且可关闭。

真实降低饱和度需要正确的颜色处理；半透明青色遮罩不等于降饱和。R1 验证最小后处理通道，首版不引入复杂 Shader 框架。基础声音先做短反馈，环境高频处理、复杂混音和空间音效留到后续。

设置提供总强度（关闭/弱/标准/强）与暗角、准星、纹样、低精力闪烁的独立控制；尚未实现的效果不放空开关。默认避免闪烁，保留稳定 HUD 和声音反馈，关闭滤镜不能关闭能力或改变精力费用。低精力时不弹“精力不足”打断瞄准。

温度色调与专注滤镜不能各自无上限叠加：专注画面优先保证瞄准清晰，温度 HUD 继续显示，环境色调减弱；退出后恢复用户设置。强模糊、强色差、扭曲、大型技能 UI 不在默认设计中。

## 6. 背负装备：首版合同

### 6.1 三个视觉槽与物品所有权

近战槽识别剑和斧，盾牌槽识别盾牌，弓槽识别弓和弩；后续由明确分类支持 Wildcraft 装备和 Fuse 宿主。三个槽只指向已有物品，不能放入、取出、掉落或复制出第二份装备，不增加真实容量。

用户已确认“实际使用后登记”：以服务端可确认的有效攻击、斧操作、举盾、拉弓/装弩等动作登记，单纯滚过快捷栏不刷新历史。具体触发与验收见 [P3.1 规格](P3.1-SPEC.md)。

维护规则：

- 记录三类最近装备的定位信息，读取当前真实 ItemStack 的模型、染色、附魔外观及允许的组件，不按物品名称写死模型。
- 耐久、名称、模型组件或 Fuse 改变后更新显示；换槽、丢弃、放箱子、消耗、损坏和死亡后重新验证归属。
- “同 ID 的两把剑”不等于同一把剑。先验证槽位定位、组件签名和库存变更跟踪方案；无法唯一定位时清空该视觉记录、等下次使用，不显示已丢失的复制快照。
- 不预先给所有原版物品增加永久 UUID。若实测必须引入物品身份组件，再说明对堆叠、复制和旧数据的影响，定稿后实施。
- 一般死亡按真实库存结果清理；保留物品时也重新校验引用。跨维度、重连与重新进入观察范围补发当前有效显示。

### 6.2 显示、装备冲突与当前滑翔行为

| 状态 | 手部与背负表现 |
| --- | --- |
| 正常持剑/盾/弓 | 已实际显示在主手或副手的同一物品不再背负；其他已登记装备可以背负 |
| 滑翔 | 双手抓伞；已登记且仍真实拥有的收起装备可背负。物品即使仍在主副手格里，也按“手中未显示”判断 |
| 空中拉弓/林克时间 | 弓在手中，背部对应弓隐藏；已登记剑、盾按可用挂点显示，不能再给拉弓双手叠一份盾模型 |
| 鞘翅 | 鞘翅优先；首版至少隐藏冲突的盾/大型弓，不以严重穿模作为可接受结果；完整腰侧调整在 P10.2 |
| 披风、护甲 | 以人物身体骨骼为挂点，测试宽/窄手臂、穿甲、潜行和游泳；未知大模型可按兼容规则隐藏，完整适配后补 |

首版以背部斜跨近战、反向斜跨弓、偏置贴背盾作为研发布局，逐项用实机确定尺寸。第一人称不绘制自己的背负物品；其他玩家的背负仍应可见。首版允许瞬时切换，拔出/收回动画留到 P10.2，不延迟真实快捷栏切换。

现有滑翔伞的独立槽是“真实装备槽”，这里三个槽是“视觉记录”。两者不能合并或相互替代；不擅自添加折叠伞背负模型或第四个视觉槽。

### 6.3 联机与性能

服务端维护有效登记，客户端只渲染服务端允许的展示状态。向跟踪玩家发送三个必要的视觉描述，不广播全背包或容器内容；Fuse 同步有界的显示摘要，不发送任意嵌套材料数据。需要特殊/私有组件的未知模型使用明确回退，不承诺兼容所有第三方物品。

按库存/组件/状态变化更新缓存，渲染阶段不扫描背包、不重复解析模型。允许有界的低频一致性检查，不能退化成每帧全量扫描。双客户端验证必须覆盖 A 看到 B 更换、丢弃、断线和重进观察范围，而非用一个客户端的 TCP 连接代替。

## 7. 温度与料理：重新界定 P4

### 7.1 环境读数与玩家伤害分开

首版目标环境温度由群系基础值 + 当地有效天气 + 水中降温 + 岩浆/火源附近升温组成。下界和未知群系使用明确默认分类；不把 Minecraft 原版气候值直接宣称为摄氏度。

显示使用极冷、寒冷、偏冷、舒适、偏暖、炎热、极热七档或等价的低干扰刻度；具体阈值由测试确定。变化逐渐趋近目标，离开水/热源后局部影响逐渐消退，并用阈值滞回避免提示抖动。重连后按当前位置重新计算，不把读数变成必须持久管理的体温。

天气需判断当地实际雨雪、遮蔽和维度，不能只因全世界下雨就给室内、无降水群系或下界一律降温。只扫描已加载范围内有限距离的热源，考虑距离、点燃状态、上限和更新间隔；不为查温度强制加载区块，不让堆叠火源无限升温。遮挡算法与数值在 P4A 具体规格中定稿。

明确的验收反例：雪原很冷但不自动冻伤；沙漠炎热但不扣血；普通泡水降温但不失温；岩浆旁升温但不新增热伤害。原版接触岩浆、燃烧和细雪冻结照常。温度不额外增加攀爬、滑翔或疾跑费用，也不让普通电池/机械失效。

P4A 先交付读数、HUD、轻量色调与环境提示；呼气粒子、热浪可后续打磨，不用遮挡瞄准的强扭曲替代反馈。不做真实体温、湿度、风寒、饮水、强制保暖装备、复杂海拔/昼夜模型。P10 可再评估轻量昼夜/高度表现，不默认升级成负面状态。

### 7.2 料理作用与实际烹饪流程

P4B 完成原版食材 → 投入/烹饪 → 领取 → 食用 → 效果结束的闭环，明确有效食材、数量、产出、失败输入、满库存、取消/退出、两个玩家同时取用的规则。料理界面和载体尚未在这批设计中定稿，进入 P4B 时形成具体方案；不要提前新增大量锅具、矿物或材料链。

| 效果类 | 规划中的用途 | 禁止误解 |
| --- | --- | --- |
| 环境保暖/清凉 | 减轻冷热表现、提供清晰的舒适度说明 | 不以吃料理为进入雪原/沙漠的通行证 |
| 细雪保暖辅助 | 减慢原版冻结累积、延长危险前窗口、加快离开后的恢复；至少一个有实测价值的有限辅助 | 不赋予全面冻结免疫；无原版防护时久留仍有危险 |
| 耐热辅助 | 普通高温反馈更舒适；未来特殊危险需独立设计 | 不自动等于原版抗火，不允许因此泡岩浆 |
| 精力通用料理 | 加快允许条件下的恢复、临时提高有效上限、降低特殊动作费用 | 不修改历史最高等级；不专门建立“林克时间专属资源” |

原版皮革防护、冻结伤害和抗火效果仍按原版规则起作用。保暖不另造一套冻伤计量条；耐热料理如果首版只改善表现，配方和说明必须如实表达，不能宣传不存在的伤害保护。

精力料理在原文中是后续示例，并非要求一次做完所有类型。P4B 建议先完成一个通用效果，例如提高原本允许恢复时的恢复速度；临时提高上限、降低费用放入 P9.1 的完整联动，具体效果列表随料理规格定稿，未采用的示例保持候选。

精力临时上限、降耗和恢复增益采用独立效果数据。当前 `StaminaData` 在构造和消费时按历史等级上限截断，不能只在 HUD 上多画一截来实现临时精力。实现临时上限时须共同更新有效上限计算、保存和恢复边界：基础上限来自历史峰值，临时上限来自效果；效果到期夹到新上限，不降低历史峰值，也不免费回满。保留格式 1 的读取路径；是否需要格式 2 在对应阶段规格中说明，不能先删旧读取。

同类效果的强度/时长、不同类共存、死亡/切维度/退出、慢动作计时、当前值截断和重连不刷新均写入规格。建议采用同类不相乘堆叠、不弱化现有更强效果、不同类型可共存的起点；最终数值和具体覆盖规则待配方设计时定稿。

P4A 单独通过不等于温度 v0.1 全部完成：原文要求的保暖料理与细雪联动在 P4B 验收后才算交付完整。

## 8. 跨系统动作与 HUD 规则

保持有限的普通、攀爬、滑翔、空中专注状态，统一检查转换条件；仅在现有结构确实出现冲突时抽取共同判断，不先建立大型技能框架。

| 转换 | 规划规则 |
| --- | --- |
| 攀爬 → 滑翔 | 保持现有空中重新按跳跃键开伞，抓墙结束，不双重扣费 |
| 滑翔 → 取出弓 → 拉弓 | 先收伞并恢复物品使用；满足条件才进入专注；不能一边双手抓伞一边射箭 |
| 攀爬 → 空中拉弓 | 先离开抓墙，再允许专注；不凭持弓自动取消所有攀爬操作 |
| 专注 → 松弓 | 按原版规则射箭或取消，退出慢动作，只执行一次；不会自动重新开伞 |
| 拉弓 → 开伞 | 遵守物品使用与双手持伞互斥；建议先结束拉弓再按跳跃开伞，持续使用键不与开伞反复抢状态；在 P3.2 具体规格定稿 |
| 任意特殊动作 → 耗尽/死亡/禁止状态 | 清理当前动作和特效；伞装备/背负引用按各自保存规则处理；不自动恢复临时动作 |

HUD 按新设计收敛到经验条区域：特殊动作/必要恢复期间显示精力，结束并恢复后回到原版经验逻辑；经验数值本身、当前等级、附魔消耗和历史峰值继续正常记录。骑乘跳跃条、创造/旁观、0 级、隐藏 HUD、屏幕缩放与其他提示需有明确显示优先级。温度用小型独立提示，不占成第二条常驻大资源条；林克时间不增加技能条。

背负只消费这些动作的“当前视觉占用”结果，不决定能否攻击、是否扣费或是否拥有物品。视觉关掉也不改变机制。

## 9. 技术栈、模块与保存方案

继续固定已验证组合：Minecraft 26.3、JDK 25、Fabric Loader 0.19.5、Fabric API 0.161.0+26.3、Loom 1.18.2、Gradle Wrapper 9.7.1；macOS + IntelliJ 为主。此次不追新版本，不把初版 Temurin 建议当成要求替换已工作的 Homebrew JDK。

仍为一个 Mod、一个 Gradle 项目，公共/客户端分离。新增职责按实际阶段建立：

| 职责 | 建议归属 | 边界 |
| --- | --- | --- |
| 共享精力与有效上限 | `player` | 保存历史进度，提供消耗/恢复规则；不依赖具体滤镜或料理界面 |
| 攀爬/滑翔/空中动作转换 | `traversal` | 复用已有碰撞与移动路径，避免两个系统写位置 |
| 林克时间资格、会话与时间接管 | `focus` | 服务端决定是否允许和费用；单人/多人实现显式区分 |
| 背负登记、引用与同步 | `equipmentvisual` | 指向真实库存，输出有限展示数据，不创建装备库存 |
| 目标温度与来源 | `temperature` | 只算环境与采样；不默认推导伤害或硬核生存状态 |
| 料理规则、成品与效果 | `cooking` | 产生原版效果或专用效果，不反向控制角色渲染 |
| 玩家挂载、滤镜、声音、HUD 与设置 | 客户端 `render` / `hud` / `input` / 必要 `screen` | 帧级表现；没有服务端资源和伤害决定权 |
| 风与天气 | `weather` | P10 提供统一环境输入，复用 P4A 天气修正，避免双倍计算 |

不现在创建这些空包，不引入数据库、云服务、跨加载器框架或动画/配置/物理大依赖。先检查已有 API、原版扩展点和小范围 Mixin；确需新增生产依赖时另行评估版本、许可证、服务端支持与用户授权。

| 数据 | 保存/同步方案 | 重连、死亡和升级原则 |
| --- | --- | --- |
| 历史等级与精力 | 保留现有 Attachment；未来效果扩展保留格式 1 读取 | 不重置历史；不因登录刷新资源 |
| 滑翔伞 | 保留现有独立真实装备附件 | 继续现有掉落/保留物品规则 |
| 背负记录 | 小型可版本化引用；同步有界的渲染描述 | 加载后先查真实库存；不以序列化副本恢复一件物品 |
| 林克时间、时间接管、滤镜过渡 | 临时会话，状态按需同步 | 不持久恢复动作或世界减速；停止/失联清理 |
| 环境温度 | 目标与当前显示状态；仅给本人必要读数 | 按当前位置重算；不是持久体温/离线伤害 |
| 料理成品 | 物品组件记录效果种类、强度、时长和规则版本 | 不依赖再次随机计算；库存移动保留内容 |
| 活跃料理效果 | 优先原版效果生命周期，必要时附加可版本化数据 | 明确暂停/离线/死亡策略，重连不刷新持续时间 |
| 能源/设备/Fuse | 继续初版物品组件、Block Entity、机械实体与必要世界保存 | 能量和材料只存在一个有效所有者，不因慢动作或重载重复产出 |

## 10. 原有后半程范围完整保留

P5 区分红石信号与可消耗电量：固定能源无限但输出限速，充电器负责充电，移动机械使用有限电池。红石块随主体移动后不能继续获得固定无限供能。温度不干预普通电池容量与机械可用性。

| R1-05 验证下降和撤销 | 耗尽、松弓、落地、死亡、切维度、退出/重开、开放 LAN、外部改速 | 没有无限滞空、摔落免疫或世界卡在慢速 |
| R1-06 验证背负呈现入口 | 一剑一盾一弓的本地模型挂点，滑翔收起与物品渲染状态读取 | 仅确认技术接口，不把实验模型当正式 P3.1 完成 |
| R1-07 输出结论 | 成功范围、失败项、推荐实现、性能/兼容代价及待定参数 | 结论支持 P3.2，或明确暂停该分支并推进可独立阶段 |
| P3.1-01 定稿登记与视觉规则 | 最近使用定义、相同物品定位、手/背占用、鞘翅/披风最低处理、HUD 切换表 | 关键产品行为可检查，数据所有权清楚 |
| P3.1-02 完成三类登记与失效 | 基于真实库存的视觉状态及必要同步 | 换槽/损坏/丢弃/箱子/死亡不出现幽灵物品 |
| P3.1-03 完成游戏表现与双客户端验证 | 原版物品渲染、本人第三人称、另一玩家观察、滑翔和融合 HUD | 原有 P0–P3 回归通过；记录真实双客户端证据 |

R1 使用独立研究分支和测试代码；实验成功后再提取经过验证的最小正式实现。P3.1、P4 的有效工作不因林克时间尚未成熟而整体停摆。

## 12. 测试与验收矩阵

| 测试层 | 重点 |
| --- | --- |
| 规则/编码 | 精力费用与时间、上限效果、背负引用、温度平滑/阈值、料理时长与覆盖、数据兼容 |
| 服务端 GameTest | 库存所有权、装备失效、料理输入产出、原版冻结和防护、事件退出、能源/箭效果执行次数 |
| 实际单人客户端 | 真假慢动作、两种视角、镜头/拉弓、缓降、滤镜开关、HUD 切换、背负挂点、暂停和保存恢复 |
| 两个实际客户端 | 背负变化可见、跟踪范围进入/离开、同时动作、网络延迟；多人全局 Tick 不被改变；后期局部效果重叠 |
| 成品与独立服务端 | 实际安装包加载、公共代码不引用客户端类、未支持模式安全禁用、保存退出 |
| 组合生存场景 | 攀爬→滑翔→弓→专注→落地；雪原→水→营火→细雪→保暖料理；Fuse 箭与慢动作；机械计时与能耗 |
| 长期/兼容 | 宽/窄手臂、护甲/披风/鞘翅、资源重载、低帧率、远端延迟、旧测试世界升级、服务器重启和区块重载 |

所有新阶段都回归 P1 历史峰值/重连、P2 碰撞与抓握、P3 专用槽/双手/开收伞。背负 v0.1 的“其他玩家可见”必须有真实双客户端证据；旧版单客户端 TCP 测试不能替代。

设置关闭视觉效果时，伤害、命中、精力、温度和动作条件应完全相同。尤其检查：零精力不能触发；满精力不能无限维持；普通冷热不新增伤害；保暖不能让无防护玩家永不冻结；副手/背部显示不能凭空产出物品。

先测固定场景中的帧耗时、服务端刻耗时、模型更新次数和网络量，再决定限制；不以“写了缓存”宣称性能达标。每阶段记录实际执行的检查与未覆盖项，远程 CI 未运行就不标通过。

## 13. 资源、版本与交付流程

美术沿用原创资源、Blockbench/可编辑源稿与游戏内验证。背负优先复用当前 ItemStack 的渲染入口；普通武器、染色盾、附魔和后续 Fuse 都需展示检查。先验证挂点和轮廓，再制作拔出动画；简单动作优先代码控制，确需外部动画库时另议。

林克时间的青绿色纹样、声音和准星元素采用 Wildcraft 原创语言，不复制塞尔达资产。资源分别检查第一/第三人称、GUI 缩放、隐藏 HUD、强弱/关闭设置、色调叠加和资源重载。

保留 `main` 的可构建状态。后续可采用 `spike/focus-time`、`feature/equipment-visuals`、`feature/focus-singleplayer`、`feature/ambient-temperature`、`feature/cooking` 等短分支；具体创建时以当前仓库为准。研究代码与成品继续隔离。

Mod 版本、机制文档 v0.1/v0.2、规划 v2、保存格式版本是四个概念。本次规划不提升 Mod 版本，不重打或覆盖 `0.1.0-dev.4` 的 JAR、源码包和验收。后续每个可运行阶段继续递增开发版本；达到组合体验里程碑并完成验收后再决定 alpha，不预先写死尚未构建的版本号。

新增玩家/物品数据保留兼容读取，使用测试世界副本验证。真实个人存档迁移、重要新依赖、公开发布或上传仍按对应明确授权执行。回退使用对应世界备份与 JAR，不宣称替换旧 JAR 会自动恢复新数据。
